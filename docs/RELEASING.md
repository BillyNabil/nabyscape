# Official releases and updates

The app checks only BillyNabil/nabyscape stable GitHub releases, at most once per 24 hours at normal startup; manual checks are explicit. Attempts are persisted separately in `update-state.json`. Diagnostics and self-tests never auto-check. Settings > Application > Updates shows installed/available versions, notes, cancellable download progress, and a separate Install and restart action. Network requests time out after 45 seconds, operations after ten minutes, with one two-second retry for rate limits/server errors. There is no polling timer.

Required future release assets: `NabyScape-win-x64-Setup.exe`, `NabyScape-win-x64-Portable.zip`, `NabyScape-Notices.zip`, `SHA256SUMS`. Existing public v2.4.2 assets remain unchanged. The updater safely reports incompatible old release assets rather than guessing names. Portable copies must use the portable ZIP and replace files after quitting; automatic install is restricted to the existing per-user `Programs/LumaIsland` installation, including legacy executable names. This is separate from the migrated `NabyScape` data directory.

Metadata and initial download URLs must exactly match the canonical HTTPS repository/tag/asset names. GitHub's signed release redirect is accepted only to its HTTPS `release-assets.githubusercontent.com` CDN; subsequent redirects fail. Size, SHA-256, PE x64 architecture and file version must match before setup becomes eligible. Checksums on the same release provide integrity, not independent publisher authenticity. Unsigned releases remain unsigned; no SmartScreen warning is suppressed. If Authenticode is present, Windows trust and revocation validation must succeed. A future signing rollout must add a pinned expected publisher/certificate policy and a signed-release requirement before claiming publisher authentication or rejecting signature removal.

Installation flushes pending Notes, saves a preference backup, settings and session before shutdown. Any save error aborts. The copied helper confirms the exact process ID, start time and installed path, then waits up to two minutes for that process to exit. It rechecks the setup hash and signature and invokes only the fixed staged setup with `--silent --launch`. Failure is logged to `NabyScape/updates/update-error.log` and setup's `install-error.txt`; check/download failures leave the running app untouched. No helper action is a general executable/URL launcher.

## Packaging and draft release

Run `./tools/Build-Release.ps1 -Tag vX.Y.Z -Dotnet ../tools/dotnet/dotnet.exe -OutputDirectory <new-directory>`. The build first checks all actual Settings section titles against scene registration; self-tests render every registered example. `tools/Test-ReleasePackage.ps1 -OutputDirectory <folder> -ValidateWinGet` independently rechecks all hashes, ZIP contents/notices, the WinGet setup hash and installed WinGet schema validation.

It rejects tag/version mismatch and reused output paths, cleans and publishes Release win-x64, runs self-tests, packages app/notices, calculates real hashes and generates WinGet manifests. The tag workflow creates a draft only after these checks. Review and publish manually; pushing a tag or publishing was not part of this implementation. Never recreate or modify public v2.4.2.

## WinGet submission

`tools/New-WinGetManifest.ps1` takes a real setup file and stable version; it emits the `BillyNabil.NabyScape` version/installer/en-US locale manifests with canonical release URL, real SHA-256, x64, user scope and `--silent` switches. Generate only against the final release binary after any signing. Check the final downloadable hash matches, then run `winget validate --manifest <folder>` using the Windows Package Manager CLI. Test installation in a disposable Windows account after quitting the app; do not test on the daily install. Submit the manifests under `manifests/b/BillyNabil/NabyScape/<version>` in a separately human-authorized microsoft/winget-pkgs PR. No submission is automatic. See [manifest documentation](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest) and [submission process](https://learn.microsoft.com/en-us/windows/package-manager/package/repository).

## Signing assessment

[SignPath Foundation terms](https://signpath.org/terms.html) require an OSI license, active maintenance, distributable releases, documented functionality and no proprietary components except system libraries. NabyScape has MIT licensing, source, docs and an existing release; maintainers must review dependency eligibility, project control/reputation, MFA for repository/SignPath access, separated roles and per-release approval, verified build origin, metadata restrictions, signing policy and privacy information before applying. This young project's acceptance is discretionary. No account, application, credentials or approval exists from this work. Do not add sponsorship credit as though accepted. A human must apply, assess eligibility and set up a controlled signing workflow. Paid certificates/services remain a human decision.

[Microsoft SmartScreen guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) explains hash and publisher reputation. Signing, WinGet availability and CI do not guarantee absence of warnings; new signed files can still warn. Never instruct users to disable or bypass Windows safeguards.
